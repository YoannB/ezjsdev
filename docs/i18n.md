# Internationalization (messages & localized URLs)

All user-facing strings live in `messages/<locale>.json`. Never hardcode labels in
components. Placeholders (`{site}`, `{count}`, `{value}`, `{name}`, `{locale}`, `{input}`)
must be preserved byte-for-byte across locales.

Localized URLs are mapped once in `i18n/routing.ts` (`pathnames`); `localePrefix` is defined
there too. A derived site adds its own routes in `site/config.ts` `pathnames` and its own copy in
`site/messages/<locale>.json`, both merged by Axons (collisions throw; see
`docs/architecture.md` → Deriving a site). The pure module `i18n/locales.ts` (testable without next-intl) is the SINGLE source
of the languages: `SUPPORTED_LOCALES` (the six that ship messages and pathnames) and the SERVED
`LOCALES` = `NEXT_PUBLIC_LOCALES` (comma-separated subset in display order, e.g. `fr,en`; empty
→ all; an unknown code throws at build). The default locale comes from
`NEXT_PUBLIC_DEFAULT_LOCALE` (empty → `en` if served, else the first served; a value outside
`LOCALES` throws at build, never a silent fallback). A single-language site sets
`NEXT_PUBLIC_LOCALES` to one code — do not edit the arrays. Routing, `generateStaticParams`,
the sitemap, hreflang, the language switcher (`constants/site.ts` `LOCALES[].active`) and the
boot script's `lang` all derive from it. Adding a SEVENTH language = a messages file, its
`pathnames` entries, `SUPPORTED_LOCALES` and the `LOCALE_META` display row. When `localePrefix` is `as-needed`, the default locale carries no URL prefix. Use `Link` /
`getPathname` from `@/i18n/routing`; never string-concatenate a locale into a path.
`sitemap.ts`, `robots.ts`, and `pathnames` must agree with `routing`.

Do NOT use the deprecated `setRequestLocale`. Propagate the locale explicitly:
`getMessages({ locale })` in the root/segment layouts, and `getTranslations({ locale,
namespace })` in Server Components and `generateMetadata`. Never call `useTranslations` inside
`generateMetadata` (it is a hook, forbidden outside a component body). Client components read
the locale from `NextIntlClientProvider` and are unaffected.

`timeZone` MUST be set in BOTH places, because the two worlds are independent (next-intl docs
_Time zone_): `i18n/request.ts` configures SERVER-only code (Server Components, Server
Actions), while `NextIntlClientProvider` configures CLIENT Components. The provider's automatic
inheritance of `timeZone` (and `locale`/`messages`/`now`/`formats`) only applies when the
provider is rendered BY A SERVER COMPONENT. In this repo `NextIntlClientProvider` is mounted
inside `providers/AppProviders.tsx`, which is a Client Component (`"use client"`), so
inheritance does NOT happen and `timeZone` must be passed EXPLICITLY on the provider
(`timeZone={TIME_ZONE}`, kept in sync with `request.ts`). Omitting it raises a non-fatal
`ENVIRONMENT_FALLBACK` on every Client Component that resolves the request context (e.g.
`Header`'s `useTranslations("nav")`) — visible in the browser console AND in the Playwright
`[WebServer]` log, but it does not fail rendering or tests.

Localized navigation uses `router.replace({ pathname }, { locale, scroll })`: the target
`locale` belongs in the OPTIONS (second argument), never inside the `to` object (whose type
accepts only `{ pathname, query? }`; putting `locale` there is TS error 2353). `usePathname`
from `createNavigation` returns a LOGICAL pathname, which is exactly the `to` key. A DYNAMIC
route whose param is translated (article slug) also needs `params`: the switcher takes them from
the page's hreflang alternate (`lib/locale-switch.ts`, see `docs/articles.md`).

## SEO metadata & formatting invariants

For SEO, metadata must be DERIVED from `routing`, never hardcoded: set `metadataBase`, and
emit canonical + `hreflang`/`alternates.languages` from the localized pathnames so every
active locale exposes the same resource with correct alternates. `pageMetadata` takes the page
`locale`: canonical and `og:locale` are the page's OWN locale (a translation canonicalized to the
default locale would be dropped from the index); `x-default` is the default-locale URL. `sitemap.ts`, `robots.ts`,
`pathnames`, and `generateMetadata` must all agree with `i18n/routing.ts`.
The HOME has its own localized `generateMetadata` (`app/[locale]/page.tsx`, messages
`meta.home.title` / `meta.home.description`, `title.absolute`); `app/layout.tsx` only holds the
site-wide defaults (title template, `metadataBase`). A derived site rewrites `meta.home`.

Format dates, numbers, lists, and plurals through the next-intl formatter APIs — do NOT
assemble them by hand (hand-rolled formatting is a localization bug waiting to happen and a
hydration risk). Message keys and localized slugs are STABLE identifiers: never use a
translated string as a route id, and never let a key's meaning drift across locales.
